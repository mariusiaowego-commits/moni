# 案例库顶部 Dashboard（A 区）架构方案

基线：worktree `docs/sprint-evidence/sprint-79/design/prototype-v2.html`、`filter-mock.html`；后端 `moni/cases/repository.py:919-1036`、`moni/web/routes/cases.py:139-154`。
视觉约束：A 区保持「无框（`--background`）+ 上下 `1px --border` 细线 + 0 圆角」，不引入新色板，不用渐变/发光/玻璃/炫技图表/emoji，不靠说明文字凑数。

---

## 1. 诊断：现在为什么单薄

现在的 A 区是一条 78px 高的 4 格数字带（`432 案例 / 137 高价值 / 305 机构 / 10 业务场景`），单薄的真实原因有四个：

1. **只有总账，没有结构**：4 个数只回答了「一共多少」，没回答「432 条里到底什么最多」——是产品发布多还是 AI 落地多？是银行多还是互联网多？用户进页面第一眼得不到任何行业判断。
2. **只有死数字，没有可点入口**：4 个数全只读，看完后必须去 B 区逐个点开胶囊才能看到分布；而「8 类、5 行业、10 场景」本来就是现成的全局导航图。
3. **垂直体量撑不住首屏**：顶栏 56px、下面 B 区是 `--muted` 暖棕控制带 + C 区白底 12px 圆角大卡，中间夹一条 78px、透明底、只有两行小字的 A 区，视觉重心全被 B/C 吸走，A 区像一条页眉而不是概览。
4. **缺「谁最活跃」的锚点**：同业分析最关心「哪类动作最多、哪个场景最热、哪家机构最活跃」，现在一个都没露出来。

## 2. 三套 Dashboard 架构方案

把 A 区从「1 层数字」升级为「**上层总量 KPI + 下层三维度结构分布**」，整体仍在上下两条 `1px --border` 之间（无卡片外框、0 圆角），用一条 `1px` 内部分隔线分成两段：

- **放哪些信息 & 回答什么问题**：
  - 上层 4 格：总量、高价值密度、覆盖机构广度、场景覆盖度（「盘子有多大、值不值得看」）。
  - 下层 3 列（各固定 4 行）：**类型 Top 4**（「同业主要在做什么动作」）、**行业分布**（「谁在主导这些动作」，`保险 2 + 证券 2` 合并为第 4 行或各自列出）、**场景 Top 4**（「热度集中在哪些业务场景」）。
- **布局与密度**：
  - 上层：`grid-template-columns: repeat(4, 1fr)`，数字 `28px/600 tabular-nums` + 标签 `13px/400 --muted-fg` 同行基线对齐（省出纵向高度，1024 改 `24px`）。
  - 下层：`grid-template-columns: repeat(3, 1fr)`，列间 `1px --border` 竖线 + `padding: 0 20px`（1024 下 `0 12px`）。每列标题 `12px/600 --muted-fg`，4 行数据行高 `26px`（13px 标签左对齐 + 纯 CSS 实色水平比例条 `height: 6px; background: --foreground; border-radius: 2px;` + 右对齐 `12px mono` 数字）。总高 ~214px，在 768 屏上留给 B+C 仍有 >430px。
- **与 B/C 的区分**：A 区无背景色（透出 `--background` 89.4）、0 圆角、仅上下及内部分隔细线；B 区为 `--muted`（79.9）内凹控制条 + 6px 圆角；C 区为 `--card`（98.9）独立白卡 + 12px 圆角。三档明度与圆角完全不破坏。
- **数据来源与 SQL 口径**：直接复用 `GET /api/cases/stats`，仅需在 `CaseRepository.stats()` 补 3 个整数并修正 `total` 过滤条件（详见 §5）。
- **成本与风险**：**0.5 人日**（纯 CSS grid + 原生 `<div>` 比例条，零图表库依赖）。唯一风险：长类别名在 1024 下要 `text-overflow: ellipsis` 防撑破行。
- **空态 / 加载 / 缺失**：加载中数字显示 `—`、比例条置空占位（`background: --muted`）；某维缺失或为 0 显示 `0` / 隐藏空行；全库 0 案例时保留上层 4 个 `0`，下层显示一行灰字 `暂无分布数据`。

## 3. 推荐与取舍

**明确推荐：方案 1（双层无框概览带：上 4 格 KPI + 下 3 列可点击结构分布条）。**

- **一句话说清第一眼得到什么**：第一眼同时看清**盘子规模（432 / 137 高价值 / 305 机构 / 10 场景）**与**行业结构重心（类型、行业、场景各自 Top 4 谁占大头）**，且点任意一条分布条就能直接下钻筛选。
- **为什么不选 2/3**：方案 2 丢了「类型 8 类」和「行业 5 类」结构；方案 3 把具体案例塞进 A 区，模糊了 A（统计）和 C（卡片）的边界。方案 1 把「统计数字」和「结构比例」严丝合缝地装在同一个无框区域里，既撑起了承载感，又守住了三层视觉语言。

## 4. 交互口径（写死，防止实现打架）

| 区块 | 筛选条件变化时是否重算 | 口径说明 |
|---|---|---|
| **A 区全部数字（上层 4 个 KPI + 下层 3 列分布条）** | **不重算，始终保持全库截面** | ①「当前命中数（如 `137 条`）」已由 B 区胶囊行右端实时承担，A 区再变会双处重复；② 分布条同时是全局导航，重算会导致未选类归零、无法横向切类；③ 筛选时免去二次聚合请求。 |
| **A 区分布条选中态（联动高亮）** | **只变样式，不改数字** | 若 B 区选中了某类型/行业/场景（如 `ai_adoption`），A 区对应那一行条形与文字保持 `--foreground` 加粗高亮，其余行降至 `opacity: 0.45`；点击高亮行等价于再次点击取消该筛选。 |
| **B 区胶囊右端 `.fhit` 与面板内 `.fopt__n`** | **随筛选实时变化** | 严格按当前筛选（面板内排除自身维度）计算真实命中数。 |

## 5. 数据契约与 SQL 口径

复用现有 `GET /api/cases/stats`（`moni/web/routes/cases.py:139-154`），**不新增端点**，只需在 `CaseRepository.stats()`（`moni/cases/repository.py:999-1036`）做如下对齐与增补：

1. **统一过滤口径**：现有 `stats()` 第 1002 行 `SELECT COUNT(*) FROM cases` 未过滤占位行和软删除，应统一为 `WHERE subject != '__processing__' AND case_lifecycle != 'archived'`（与 `aggregate_cases_by_*` 一致）。
2. **增补 3 个整数字段**（直接写进 `stats()` 返回字典）：
   - `enterprise_count`：`SELECT COUNT(DISTINCT COALESCE(subject_enterprise_id, subject)) FROM cases WHERE subject != '__processing__' AND case_lifecycle != 'archived'`（口径说明：当前副本库为 `305`，含规范企业 94 家 + 未归并长尾主体 211 家；若前端显示「已入库规范企业」则取 `COUNT(DISTINCT enterprise_id) FROM case_enterprises` = `94`，**两选一写死，本方案按 brief 305 口径**）。
   - `scenario_count`：`SELECT COUNT(DISTINCT scenario_code) FROM case_scenario_links`（实测 `10`）。
   - `category_count`：`SELECT COUNT(DISTINCT case_category) FROM cases WHERE case_category IS NOT NULL AND subject != '__processing__' AND case_lifecycle != 'archived'`（实测 `8`）。
3. **已有四维数组直接复用**：`by_category`（取前 4 项用于「类型」列）、`by_industry`（全部 5 项，前端将 `保险`+`证券` 或尾部合并至 4 行）、`by_scenario`（取前 4 项用于「场景」列）。
