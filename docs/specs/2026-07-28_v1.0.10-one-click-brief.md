# Tech Spec: 一键简报 (v1.0.10)

> moni · 2026-07-28 · Draft  
> 分支: `feature/v1.0.10-one-click-brief`

## 1. 现状架构（简）

```
UI 分享页
  → POST /api/share/estimate  (可选)
  → POST /api/share           (write_manifest → DB pending + ~/.moni/queue/*.json)
  → POST /api/share/worker/run (用户手动)
  → default_worker.sh
       BB_FETCH → SUMMARY_GEN → build prompt → hermes → write artifact
  → GET /api/share/tasks      (poll progress_stage / progress_pct)
```

**痛点落点**：文章选择与 enrichment 选项在前端；worker 启动是第二按钮；无 business_value；pin 未直连 brief。

## 2. 目标架构

```
UI「用当前 Pin 生成简报」
  → POST /api/share/brief { format, title?, options? }
       1. SELECT article_id FROM article_pins ORDER BY pinned_at
       2. build opinionated payload (defaults)
       3. validate_manifest + write_manifest
       4. launch_worker()   # auto
       5. return { share_id, status, article_count, estimated_sec? }
  → worker (扩展)
       enrich_each_article:
         - ensure ai_summary
         - ensure fact_check_*
         - ensure business_value_*
         - optional BB fields if requested
       then format render (existing)
  → UI poll GET /api/share/tasks 或 GET /api/share/tasks/{id}
```

## 3. API

### 3.1 `POST /api/share/brief` (新)

**Request**
```json
{
  "format": "markdown",
  "title": "可选，html_landing/pdf/info_graphic 等需要时",
  "options": {
    "include_abstract": true,
    "include_fact_check": true,
    "include_business_value": true,
    "include_quality_score": true,
    "bb_enhance": false
  }
}
```

- `options` 全可选；缺省 = brief 官方默认（全 true，bb false）
- **article_ids 不接受客户端传入**（brief 语义 = 当前全部 pin）。自定义集合走旧 `POST /api/share`

**Response 201**
```json
{
  "share_id": "...",
  "status": "pending",
  "article_count": 10,
  "worker": { "started": true, "already_running": false, "pid": 12345 }
}
```

**Errors**
- 400 `no_pins` — 当前 0 pin
- 400 format validation（复用 formats.py）
- 409 可选：若已有同 pin-set + format 的 running brief（**v1 可不做**，允许并行）

### 3.2 现有 API 行为微调

| API | 变更 |
|-----|------|
| `POST /api/share` | 可选 query/body `auto_start=true`；brief 专用 endpoint 更清晰，旧 API 加 auto_start 作兼容 |
| `GET /api/share/tasks` | 无强制变更；progress_stage 枚举扩展 |
| `POST /api/share/worker/run` | 保留；brief 路径通常不再需要点 |

### 3.3 Progress stages（扩展）

| stage | pct 建议 | 含义 |
|-------|----------|------|
| `queued` | 0 | 已入队 |
| `loading_articles` | 10 | 读正文 |
| `enrich_summary` | 25 | 摘要 |
| `enrich_fact_check` | 40 | 事实核查 |
| `enrich_business_value` | 55 | 业务价值 |
| `bb_fetch` | 50 | 可选 BB |
| `building_prompt` | 65 | 拼装 |
| `invoking_llm` | 75 | 格式渲染 LLM |
| `writing_artifact` | 90 | 落盘 |
| `done` / `failed` | 100 / — | 终态 |

> 实现约束：bash worker 改 stage 成本高；**优先**在 Python 侧 enrichment 写 stage，或 brief 模式走 `python -m moni.share.brief_worker` 薄封装（若改 bash 风险大，Step 2 选「最小 diff：bash 调 python enrich 模块」）。

## 4. 数据模型

### 4.1 Migration 020（建议）

```sql
-- moni/db/migrations/020_business_value.sql
ALTER TABLE articles ADD COLUMN business_value_score INTEGER;  -- 0-100
ALTER TABLE articles ADD COLUMN business_value_note TEXT;     -- 2-4 句中文
ALTER TABLE articles ADD COLUMN business_value_at TEXT;
ALTER TABLE articles ADD COLUMN quality_score INTEGER;       -- 0-100，无 bb_score 时用
ALTER TABLE articles ADD COLUMN quality_score_at TEXT;
```

- **article 级缓存**：换 format 再 brief 时跳过已 enrich 的篇
- 失效策略：v1 不自动失效；用户可后续加「强制刷新」

### 4.2 share_tasks

无需新表。可选在 manifest payload 记 `"brief": true` 供 UI 高亮。

## 5. Enrichment 语义

### 5.1 摘要
- 已有 `ai_summary` → 复用
- 否则 `summary_gen` / hermes 生成，写回 `ai_summary`, `ai_summary_at`, `has_ai_summary=1`

### 5.2 事实核查
- 已有 `has_fact_check=1` 且字段非空 → 复用
- 否则 LLM 输出结构化结论 → `fact_check_conclusion` / `method` / `note` / `fact_checked_at`

### 5.3 质量评分
- 若 `bb_score` 有值 → 展示用 bb_score，不重复打 quality_score
- 否则 LLM `quality_score` 0–100（信息密度/可操作性/来源可靠）

### 5.4 业务价值（新）
固定 persona（可配置进 prompt 文件 `moni/share/prompts/business-value.md`）：

> 读者：国内银行/支付机构的同业情报与数字化产品从业者。  
> 维度：监管影响、产品对标、技术可借鉴、客户经营、风险合规、优先级（本周/本月/关注即可）。  
> 输出：`score` 0–100 + `note` 2–4 句中文（必须点名「对己方可能意味着什么」）。

## 6. Worker 集成策略

**推荐（最小风险）**：

1. 新增 `moni/share/enrichment.py`：纯 Python，输入 article_id 列表 + flags，逐篇 ensure 字段，更新 progress
2. `default_worker.sh` 在 SUMMARY_GEN 段落后调用：
   ```bash
   python3 -m moni.share.enrichment --task-id "$task_id"
   ```
3. brief manifest 带 `include_business_value: true` 等 flags；旧任务缺省 false 行为不变

**备选（更大）**：brief 完全新 worker entrypoint — 仅当 bash 钩子不够时采用。

## 11. 评审补丁（实现必须遵守）

### 11.1 formats.py
所有 payload 增加（默认 false，brief 路径显式 true）：
- `include_business_value: bool = False`
- `include_quality_score: bool = False`（可选；MVP 可先不算独立列）
- `brief: bool = False`

### 11.2 Progress 单调序列（BB off 跳过 bb）
`queued(0) → loading(10) → enrich_summary(25) → enrich_fact_check(40) → enrich_business_value(55) → building_prompt(65) → invoking_llm(75) → writing_artifact(90) → done(100)`

### 11.3 超时
- 每步 hermes cap（如 90–120s）
- enrich 总预算（如 480s），超时 partial + message
- estimate 按「缺 ai_summary / 缺 fact_check / 缺 business_value 的篇数」估算

### 11.4 产物契约（markdown brief）
1. 标题：同业简报 {date}
2. Executive rollup：按 BV score 前 3–5 条一句话
3. 逐篇（BV desc）：标题 / 来源 / 质量分 / 业务价值分+note / 摘要 / 事实核查 / 链接
4. enrich 失败篇：标注「本篇 enrichment 部分失败」仍输出可得字段

### 11.5 Worker 顺序修正
enrichment 必须在 **拼 article_content / build prompt 之前完成**，或 enrich 后 **强制 re-read DB** 再拼装——禁止 snapshot 旧 content 导致 BV 进不了产物。

### 11.6 fact_check 幂等
以 `fact_check_conclusion IS NOT NULL AND length>0` 为准；写回时同步 `has_fact_check=1`。
