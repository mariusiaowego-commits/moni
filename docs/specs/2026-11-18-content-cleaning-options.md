## 0. 口径（按 dad 2026-11-18 澄清）

「数据清洗」= 内容进来后的全部劣质内容治理：

1. 正文去杂质（尾巴、乱码、实体、frontmatter、HTML 残留）；
2. 黑白名单 / 主题门控这类**准入过滤**；
3. 重复、测试数据、垃圾广告；
4. 前端可操作 + 可对外汇报。

已确认：**空正文不丢**（部分信源受合规限制只能抓标题，dad 后续手工导入正文）。

## 2. 我的三套方案

### 甲：清洗中心（执行 + 报告）

- **一句话**：给「清洗」一个页面：先预演，再一键执行，最后出一张可截图/可导出的战报。
- **后端**：`moni/fetch/content.py` 纯函数（修幂等 bug、统一杂质规则）；migration 047
  （`articles.content_*` + `cleaning_runs`）；`/api/cleaning/preview|apply|runs|report`；
  `clean-articles` 默认 dry-run。
- **前端**：顶部/设置新增「数据清洗」入口：概览卡（总数/空/短/杂质）、预演 diff、执行按钮、
  历史记录、导出报告。
- **对外报告**：`清洗报告-YYYYMMDD.md` + 战报卡片：扫描 5,330 → 修复 491 → 移除 38,073 字 →
  修复 32 篇误清空 → 清 4 条测试数据；按源明细 + 5 条前后对照。
- **成本**：5-6 人日。
- **风险**：误删（预演 + 只改确定性杂质 + 二次运行 changed=0）。
- **不做什么**：不动过滤规则、不调 LLM、不自动丢空正文。

### 乙：准入规则中心（过滤 + 预演 + 复核）

- **一句话**：把「什么内容不该进库」从 7 条藏在库里的黑名单，变成可预演、可统计、可回捞的规则。
- **后端**：规则加「豁免词」（如命中「扫码」但含「扫码支付」则放过）；新增只读预演
  （对近 30 天/全库算出会拦哪些，不写库）；启用后进 basket 带规则 id；basket 支持批量回捞；
  测试源守卫（`s`/`testsrc`）。
- **前端**：改造现有过滤配置页：每条规则加豁免词 + 「历史库预演」按钮（命中列表 + 上下文）；
  菜篮子加「本次清洗移入」筛选 + 一键回捞。
- **对外报告**：本周拦截 X 条，按规则分布（广告 45 / 赠书 6 / 测试源 4），误杀 0。
- **成本**：5-6 人日。
- **风险**：短词误杀（「扫码」295 篇里 36 篇是「扫码支付」）→ 预演 + 豁免 + 可回捞。
- **不做什么**：不做 LLM 广告分类、不做跨源去重、不批量删历史。

### 丙：信源契约与体检（只读，建议并入甲）

- **一句话**：给每个信源标一句「它本来应该长什么样」，这样「空」和「短」才知道是正常还是坏了。
- **后端**：`sources.content_contract`（`full_text / snippet / short_form / title_only`）；
  体检按契约判偏差：`title_only` 源空正文 = 正常；`full_text` 源空 = 故障。
  只读 `content-audit`，输出每源健康分。
- **前端**：信源列表加契约选择 + 健康分列；周报一张表。
- **对外报告**：17 个信源里 2 个异常（huxiu 44% 空、bestblog-yt 98% 空），其余正常。
- **成本**：2-3 人日（并入甲后 +1 人日）。
- **风险**：无（只读 + 配置）。

## 4. 我的建议

**开一个 sprint：甲 + 丙（清洗中心，带信源契约）**，约 6 人日。

理由：

1. 491 篇杂质和 32 篇误清空是**客观脏数据/真 bug**，没有语义争议；
2. 直接满足「我激活就能清洗 + 对外汇报」；
3. 信源契约必须和状态一起做，否则报告会把 666 篇合规空正文误报成故障；
4. agy 的「正文升级」很小（半天），顺手并进甲；跨源去重只有 1%，不进。

**乙（准入规则中心）排下一个 sprint**。它价值也高，但涉及误杀，需要单独的预演/回捞闭环，
不适合和清洗混在一个 PR。

**不建议单独开 sprint 的**：

- 跨源去重（1%，且「同题不同角度」难判）；
- trafilatura 全文补齐（新依赖 + 反爬 + 合规，属 V2）；
- LLM 质量打分（和已有 BV 十维重复）。
