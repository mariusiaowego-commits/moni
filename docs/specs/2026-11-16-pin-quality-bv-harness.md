## 1. 结论

**质量分**回答「稿子齐不齐」，本地算，5 分制（两位小数），只在 Pin 列表出现。它不评内容好坏，也不再抄 BestBlogs 的 `bb_score`。

**通用业务价值**回答「这篇对我方有没有用」，10 个维度各 0–10，每维必须有正文原句支撑，程序按权重加总。模型不给总分。检查不过重跑一次，仍不过标「待复核」，排在通过项之后。

**方向业务价值**（V2）回答「按我选的主题，这篇有没有用」。它是第二套题目，不是更高档的分数。保留完整设计，但不在 V1 实现。

三处关键取舍：

- 总分只是一个排序键，不是结论。卡片上同时给维名标签，让人不点开也知道这篇强在哪。
- 决策窗口有 90 天地平线，会过期。过期时在界面上标出来，不改库里的分，也不每天重算。
- 库里已有的旧分不迁移、不回填。靠 status 和公式版本识别，读到就按新规则处理。

### 2.1 BestBlogs 的真实实现（我已下载原文核对）

仓库 `github.com/ginobefun/BestBlogs`，文件树共 283 项。按文件名检索 `prompt|score|rating|eval|quality`，只命中 `flows/Dify/` 与一篇订阅源文章，**没找到独立评分代码**。评分都在 Dify 工作流里。

- `flows/Dify/ArticleAnalysisFlow.md`（60,339 字节）
  - 内部评分是 **4 维加权 + 调整分**：内容深度 0–30、相关性 0–30、写作质量 0–20、实用性和创新性 0–20；另加「综合评分调整 −10~+10」；`score` 输出 0–100 整数。
  - 有独立的「审核专家」节点和「改进」节点：审核给改进建议，再由模型重写摘要、观点、金句和分数。
  - 审核员**不要求引用原文句子**，也**可以改总分**。
  - 流水线是：领域分析 → 摘要/观点/金句 → 评分 → 检查反思 → 改进 → 翻译。
- `flows/Dify/ArticleFIlterFlow.md`（2,752 字节）
  - 初评尺度 **2026-05 已从 0–5 改为 0–100**，`value ≥ FILTER_MIN_SCORE_ARTICLE`（默认 30）才放行进入深评。0–5 是历史值，引用它已经过时。
  - 初评只看元信息 + 截断摘要，不读全文 —— 这一点支持我们把「本地完整度」和「模型深评」分成两层。
- `README.md`（19,913 字节）L29 / L31 / L72 对外展示的是六维「选题 / 内容 / 深度 / 实用 / 创新 / 表达」，L314–316 写明流水线是「初筛过滤 → AI 深度分析」。

下载件留在 `/private/tmp` 供复核：`bb-article-analysis.md` sha256 `b58bad58…7e73`、`bb-filter.md` sha256 `b93e3f13…d759`、`bb-readme.md` sha256 `c7b9c535…3d68`。

**结论**：对外六维和内部四维不是同一套。这支持「展示维度 ≠ 计算维度」，但不支持我们再发明一套对外维度名 —— 对外就用 10 问里达标的维名，不自造新词。

**我们与它的四处差异**，都是有意的：

| 维度 | BestBlogs | 本方案 | 理由 |
| --- | --- | --- | --- |
| 总分来源 | 模型直接给 `score` | 程序加权 | 模型口算不可复核 |
| 检查员权限 | 可改写总分与叙事 | 只能判通过/不通过 | 防止检查员顺手抹平问题 |
| 证据 | 不要求引用原句 | 每维必须引用，子串校验 | 没有引用的高分在银行场景不可用 |
| 题材 | 内容好不好读 | 对银行/支付机构的决策价值 | 读者不同 |

## 3. V1 范围

### 3.1 做什么

| 能力 | 落点 | 模型调用 |
| --- | --- | --- |
| 质量分 `pin_heuristic_v3`（0–5） | Pin 列表一列 | 0 |
| 通用业务价值 10 维 | 简报排序 + 卡片 | 每篇 ≤5 次 |
| 评分模块 | 新建 `moni/scoring/` | — |
| 迁移 045 | 加列 + 1 张表（`bv_direction*` 推迟） | — |

### 3.2 不做什么（V1）

- 不做方向配置、方向研究、方向分。设计保留在第 10 节。
- 不做服务端 `quality_stale` 布尔，不做指纹比对接口。
- 不做决策窗口的每日重算或缓存键带日期。
- 不迁移、不回填任何历史分数。

### 3.3 为什么砍方向

两个审稿人独立给出同一判断：方向分的工程量（配置表、研究版本、`running/expired` 状态、重新研究、双列展示、简报切排序）约占全稿一半，而它的价值依赖「通用分的排序被实际用过」。没有这个前提，用户无法判断方向分准不准。

V2 触发条件（grok 与 agy 条件合并后取严）：

1. 通用分上线满 10 个工作日；
2. 至少 4 份简报按通用分排序发出；
3. `needs_review + budget_skipped` 合计低于 20%；
4. 用户至少 2 次为同一主题手动二次筛文（口头提出也算）。

四条全满足才开 V2 的表和 UI。**不到就继续用通用分 + 手工筛选。**

## 4. 架构

采用 grok 的 B 方案：评分逻辑独立成包，Pin、简报、将来的 CLI 审计都只是调用方。

### 4.1 模块划分

```
moni/scoring/
  __init__.py      # 对外只暴露 4 个函数，见 4.3
  snapshot.py      # ArticleSnapshot：从 sqlite3.Row 归一化出的不可变输入
  heuristic.py     # pin_heuristic_v3（0–5）+ reading_heuristic（0–100）+ 指纹
  rubric.py        # RUBRIC_V1：10 维、权重、锚点、理由模板、禁词
  bv_pipeline.py   # 取证 → 打分 → 检查 → 重跑；返回 Breakdown，不碰 DB
  store.py         # Breakdown ↔ 文章列；质量列读写
  direction.py     # V2 才实现，V1 留空文件不建表
```

约束：

- **纯函数优先**：`heuristic` / `rubric` / `bv_pipeline` 不导入 `sqlite3`，不读环境变量，模型调用通过参数传入的可调用对象（`llm(prompt, timeout) -> (text, code)`）。
- **写库只在 `store.py`**，并且由调用方持有连接和事务。测试可以不启 FastAPI、不建完整库。
- `enrichment.py` 与 `brief_html.py` 只做三件事：把行转成 `ArticleSnapshot`、调 scoring、把结果写回或渲染。

### 4.2 数据流

```
Pin POST ──► snapshot.of_row ──► heuristic.score_quality ──► store.write_quality
                                                              (articles.quality_*)

简报 run ──► snapshot.of_row ──► bv_pipeline.score_general ──► store.write_bv
                                                              (articles.business_value_*)

简报渲染 ──► store.read_bv ──► 排序 ──► 卡片/html
```

模型调用只在 `bv_pipeline` 内部发生，与写库分离。这样「模型跑成功、写库失败」和「预算不够」是两种可区分的错误。

### 4.3 接口契约

```python
def score_quality(snap: ArticleSnapshot) -> QualityResult
def reading_heuristic(snap: ArticleSnapshot) -> int
def score_general_bv(
    snap: ArticleSnapshot,
    rubric: Rubric = RUBRIC_V1,
    llm: Callable[..., tuple[str, int]] | None = None,
    budget_s: float = 90.0,
) -> BvResult
def needs_rescore(row_status: str | None, row_hash: str | None, snap_hash: str) -> bool
```

`QualityResult`：`score, status, breakdown, error, formula, input_hash`
`BvResult`：`status, total, note, breakdown, error, content_hash, calls_used, elapsed_s`

`llm=None` 时 `score_general_bv` 返回 `budget_skipped` 而不是抛异常。这个函数不接受 DB 路径、不接受文章 id 列表以外的上下文。

### 4.4 状态机

质量：`ready` →（公式或哈希变化）→ 重算；`failed` 保留错误，下一次刷新重试。

业务价值：

```
pending → ready | needs_review | failed | budget_skipped
insufficient 是终态（同一正文哈希下命中缓存）
ready/needs_review 在正文哈希变化时回到 pending
failed / budget_skipped 不按缓存命中，下次仍调模型
```

### 4.5 失败与重试

| 情况 | 处理 | 是否重试 |
| --- | --- | --- |
| 质量公式抛异常 | `failed` + `quality_error`，Pin 不回滚 | 下次刷新 |
| hermes 非 0 / JSON 解析失败 | `failed`，分数 NULL | 下次出简报 |
| 检查两次不通过 | `needs_review`，保留加权和 | 不自动，用户可重跑 |
| 预算不足 | `budget_skipped`，分数 NULL | 下次出简报 |
| 写库失败 | 模型结果丢弃，记日志 | 下次出简报 |

任何一条都不把错误写成 0 分。

### 4.6 成本与预算

- 质量分：0 次模型调用，纯 Python，单篇 <5ms。
- 通用分：单篇 ≤5 次（取证 1、补抽 ≤1、打分 1、检查 1、重跑 ≤1）。按单步 90s 上限，单篇最坏 450s。
- 简报 10 篇最坏 4500s，远超 `ENRICH_BUDGET_SEC=900`。**V1 必须同时改预算或改成并发**，否则后半队列全部 `budget_skipped`。
  - 建议：预算按篇均 120s 分配（`remaining / 剩余篇数`），单篇取 `min(120, 剩余)`；不足 60s 直接 `budget_skipped`。
  - 这条要写进 tech-spec，不在本设计里拍死具体数字。

### 4.7 可观测性

每次评分打一条结构化日志：

```
scoring bv article=<id> status=<s> calls=<n> cache=<hit|miss> elapsed=<s> budget_left=<s>
```

简报结束打一行汇总：`scoring bv run n=<篇数> ready=<n> review=<n> failed=<n> skipped=<n> calls=<总次数>`。

V1 不加指标系统，日志够用。没有这条日志，预算问题无法定位。

### 4.8 迁移与回滚

- 045 一个文件：`articles` 加 8 列（质量 4 + 通用 4），不建方向表。
- SQLite 的 `ADD COLUMN` 多数不可逆。回滚 = 恢复备份，不是写反向迁移。所以 045 执行前必须做库备份。
- 回滚后新列留空，代码要能在「列存在但全空」的状态下正常工作（这也是首次部署的状态）。

## 5. 质量分 `pin_heuristic_v3`

### 5.1 公式

| key | 规则 |
| --- | --- |
| base | 2.50 |
| length | `len(raw.strip())`，只去首尾空白：≥5000 +1.40；≥2000 +1.00；≥800 +0.60；≥200 +0.20；否则 −1.10 |
| substance | 数字串 ≥3 处 +0.40，1–2 处 +0.20；分段 ≥4 再 +0.20；合计 ≤0.60 |
| publisher | 非空 +0.30 |
| published_at | 非空 +0.20 |

`total = round(clamp(0, 5.00, base + Σdelta), 2)`，最多两位小数。四项 + 底分合计正好 5.00，不设「调整分」。

2026-11-18 口径调整（用户拍板）：原 0–90 改为 **5 分制、保留两位小数**。映射保持单调
（25→1.40、18→1.00、10→0.60、4→0.20、−20→−1.10；8→0.40、4→0.20；5→0.30、3→0.20），
目的是与 0–100 的通用业务价值分、BestBlogs `bb_score` 一眼区分。公式名随之升为
`pin_heuristic_v3`，旧 `v2` 行在下次 Pin 页加载或 refresh 时重算。

指纹 = 公式名 + strip 后的正文 + 发布方原串 + 发布时间原串。不含标题、来源、摘要、核查、`bb_score`。

长度口径与现行 `compute_heuristic_quality` 一致（`len(raw.strip())`），不是删掉全部空白。

### 5.2 触发与刷新（三方对撞后的最终版）

1. `POST /pin`：pin 行写入成功后同步算，失败不回滚 Pin。
2. `DELETE /pin`：不删分，不改时间戳。
3. `GET /pinned`：只读，返回本行的 `quality_formula`，不做指纹比对、不写库。
4. Pin 页渲染时，某行 `quality_formula != 'pin_heuristic_v3'`（含 NULL）→ 该行先显示省略号，对该 id 发一次 `POST /api/articles/pins/quality-refresh`。刷新回来再显示。
5. **正文写回也要重算**（agy 补的一条）：任何写 `raw_content` / `publisher` / `published_at` 的路径，如果该文章在 Pin 集合里，同一事务内重算质量分。这条堵的是「Pin 时只有标题、后来补抓全文」的场景 —— 只靠公式版本判断不出来。
6. refresh 的 body 是 id 列表，上限 200，只处理仍在 Pin 集合里的 id。分享页不调用。
7. 响应 `{updated:[], unchanged:[], skipped:[]}`。公式不对、哈希不对、breakdown 为空、status 不是 `ready`，都算 `updated`。

### 5.3 字段

`POST /pin` 与 `GET /pinned` 返回：`quality_score`、`quality_status`、`quality_error`、`quality_formula`、`quality_breakdown`、`quality_score_at`。

不返回服务端计算的 `quality_stale`：判断权在前端，判据就是公式字段。

`GET /api/articles` 不返回这些字段。Pin 响应用独立模型，不要往共用 `Article` 上加。

### 5.4 Pin 列

表头「质量分」，右对齐等宽数字，宽度按两位小数收口，插在「命中标签」和「原文时间」之间。只在 Pin tab 出现。

| 状态 | 显示 |
| --- | --- |
| 公式正确且有分 | 两位小数（如 `4.80`） |
| 公式不对 / 正在刷新 | 省略号 |
| `failed` | 破折号，tip 用 `quality_error` |
| 分享页 | 只显示公式正确的行，其余破折号 |

tooltip（悬停才出现，七行）：

- 本地算的完整度，5 分制，不评内容好坏
- 四项全满才到 5.00，满分即 5.00
- 正文长度：去首尾空白后分 5 档，不足 200 扣 1.10
- 数字与结构：数字≥3 处 +0.40，1–2 处 +0.20，分段≥4 +0.20
- 发布方：有发布方 +0.30
- 发布时间：有发布时间 +0.20
- 底分 2.50

## 6. 通用业务价值

### 6.1 状态

| status | 分数 | 缓存 | 简报 |
| --- | --- | --- | --- |
| `insufficient` | NULL | 命中（同哈希） | 排除，原因「正文过短（不足 200 字）」 |
| `ready` | 加权和，可为 0 | 命中 | 纳入 |
| `needs_review` | 加权和 | 命中 | 纳入，排在所有 `ready` 之后 |
| `failed` | NULL | 不命中 | 排除，「业务价值未完成」 |
| `budget_skipped` | NULL | 不命中 | 排除，「业务价值未完成」 |
| `pending` | NULL | 不命中 | 排除，「业务价值未完成」 |

正文 <200 字：`insufficient`，说明「正文过短，未打业务价值分」，0 次模型调用。

十维全 0 且检查通过：`ready`，总分 0，说明「已评 0 分：10 问均无对应内容」。这是结论，不是失败。检查提示词必须明写「全 0 且无编造即通过」。

总分 >0 但没有一维 ≥7：说明「各维均未达 7 分；最高{维名} {n} 分」（agy 指出原句「无维达 7 分」读着像错字，已弃用）。并列取权重最高，权重相同按 6.4 表序。

旧行（`business_value_status` 为空）单独判：说明含「素材不足」或「正文过短」，或分 ≤40 且无有效说明 → 排除；其余可进。不与新规则叠加。

### 6.2 调用

单篇最多 5 次，顺序：抽证据 1、补抽 ≤1、打分 1、检查 1、重跑 ≤1。

正文 >6000 字：按段落切 ≤3000 字的窗，取 4 个（首、尾、数字/日期密度最高的两个），**拼进同一次取证**。只有代码发现引文不合格才补抽，补抽是第 2 次。

打分只看标题、400 字导语、≤8 条已校验引文。

### 6.3 证据闸门

- 最多 8 条引文；NFKC + 去空白 + 标点归一后做子串；通过后 ≥12 字。
- 短词（如「支付」）即使命中子串也丢：`dropped_evidence.reason=too_short`；编造：`not_substring`。
- 维度无有效引文且分数非 0：`min(score,3)`，`cap_reason=no_valid_evidence`。分数本来就是 0 则保持 0。
- 非整数（7.5）：该维按 0，记 `non_integer`，检查不通过。
- 禁词一份共用：值得关注 / 赋能 / 闭环 / 抓手 / 底层逻辑 / 深刻 / 凸显；正则 `(不是|并非|不只是|不仅是).{1,20}(而是|更是)`。理由命中即该轮不通过；拼说明前再滤一次，命中的维改写成「{维名} {n} 分」。
- 缺 key：该维按 0、`cap_reason=missing`、检查不通过。这与「正文没写到」不同。

| 规则约束 | 无监管机构、规章、处罚或窗口指导 | 只有「监管趋严」这类话，无文件名/机构名/条款 | 点名文件或机构，但只有大意，无条款号与生效日 | 文件全称 + 文号或条款 + 生效日；或罚单写明机构、金额、事由 |

| 资金路径 | 不涉及支付、账户或清算 | 只有「支付竞争激烈」 | 点了通道或账户类型，没写从哪到哪 | 写清从哪一方经哪些节点到哪一方 |

平均分允许：1–2 分落在 0 与 3 之间，4–5 落在 3 与 6 之间，7–9 落在 6 与 10 之间。检查员用相邻两档判断。

理由句模板（≤30 字，写入打分提示词）：

`{机构}发布{文件}，{日期}起执行，要求{义务}` · `{机构}于{日期}{动作}{对象}` · `{机构}{产品}面向{对象}，额度{数字}，条件{要点}` · `{机构}在{环节}采用{架构或组件}，控制点为{要点}` · `{机构}针对{客群}做{动作}` · `资金经{节点1}到{节点2}，走{通道或清算方式}` · `{机构}因{事由}被{处罚}，损失{金额或范围}` · `适用于{机构类型}，覆盖{客户类型}` · `{事件}将于{日期}{节点}，距今{n}天` · `需{牌照或系统}，投入约{数字}，周期{时长}`

两条容易写错的，单独重申：

- 落地门槛：「一周上线」单独出现是 6 分（时长算一类），不是 3 分；没有通过校验的引文仍封顶 3，那是闸门不是锚点。
- 决策窗口：10 分必须有可解析日期；没有日期最高 6 分。

### 6.5 加总、说明与缓存

`contribution = score/10*weight`，一位小数；`total = clamp(0,100,round(sum))`。模型给的 `score`/`total`/`weight` 一律丢弃。

说明由程序拼：取 ≥7 的维按权重取前两，理由用分号连接，截 50 字；不足两维用一维；一维没有用 6.1 的句子。

缓存键 = 归一化正文 sha256 + `bv_rubric_v1`。标题变化不失效。`failed`/`budget_skipped` 不命中。

**决策窗口的过期（提案 C，待拍板）**：

- breakdown 存 `scored_on` 与 `decision_window.evidence_dates`。
- 渲染时现场算「距该日期 X 天」。
- 若评分时不足 90 天、今天已超过，在这一维的标签/理由旁标「窗口已过（评分时 78 天）」，卡片 tip 加「可重跑更新」。
- **不改 status、不改分数、不改排序。** `needs_review` 只表示校验失败，不能被日历事件复用。

这样做的好处：不每日重算、不需要指纹接口、不撒谎。代价：库里存的是评分当时的判断，读者要靠标注自己判断。这是三方一致接受的代价。

1. `bb_score=96`，正文 strip 后 1000 字、数字 0 处、分段 <4、无发布方、无发布时间 → Pin 后 `quality_score=3.10`，`bb_score` 仍 96，`base+Σdelta=3.10`。

3. 摘要和核查有无不影响质量分；breakdown 不含 `ai_summary`/`fact_check`/`source_prior`/`bb_score`。
4. 正文不变，第二次 refresh 落在 `unchanged`；改 `raw_content` 后 refresh 落在 `updated`。

10. 检查两次不过 → `needs_review`、加权和、排在任意 `ready`（含 1 分）之后；「凸显出」不进卡片说明。旧行三态（素材不足 / 正文过短 / 80 分说明正常）分别排除、排除、纳入。

## 10. V2 附录：方向分

这一节保留完整设计，V1 不实现、不建表。触发条件见 3.3。

### 10.1 两列的含义

- 通用：不选方向，就是第 6 节的 10 维，写 `articles.business_value_*`。
- 方向 · {label}：带方向再跑一遍，写 `article_bv_direction`。通用分不动。

方向分不是第 11 维，也不乘系数。变的只是 10 个问题从哪来：来自该方向已保存的研究。两列题目不同，分数不能互比。

对外列头「通用」/「方向 · {label}」，悬停分别「固定 10 问打分，不随方向变化」/「按{label}研究 v{n}（{日期}）的 10 问打分」，共用第二行「两份题目不同，分数不能互比」。

### 10.2 配置与研究

配置项：`label`（≤6 字，过禁词表）、`brief`（必填，空的不研究）。

研究只在两处触发：保存/修改方向、点「重新研究」。每篇不重新研究。

提示词 `bv_direction_research_v1`，输入只有 label 和 brief，输出 `scope` / `out_of_scope` / 10 组维度（问题 ≤30 字、0/3/6/10 锚点、反例、理由模板）。五条硬句写死在提示词里：

1. 每个问题保留该 key 原问题的意思，只把对象换成本方向。
2. 问题一律从银行或支付机构角度问：这件事改变我方什么。
3. 锚点只写正文可见的事实：机构、文号、金额、日期、流程。
4. 不得评价写作，禁止出现深度、可读、文笔、观点、洞察。
5. 范围外内容一律记 0，不许为本方向牵强关联给分。

校验：10 key 齐、四档全、禁词与正则无命中、写作禁词无命中。不过则 `failed`。

存档：开始前插入 `running` 并把旧 `passed` 改 `expired`；返回后改 `passed`/`failed`。唯一键 `(direction_id, research_version)`。

### 10.3 门控

只看 `research_version` 最大的一行：

- `passed` 且快照等于当前 label/brief → 可用。
- `running`/`failed`/`expired`/快照不符 → 拒绝，不回退旧版。

### 10.4 打分与展示

缓存键 = 正文哈希 + direction_id + research_version。同键正文变了走 UPDATE，只有新版本才 INSERT。

卡片：`方向 · {label} {n}` chip，tip「按{label}研究 v{n} 的 10 问打分，题目不同」；简报选了方向时副标题「按方向 · {label} 业务价值排序」，排序与排除只用该版本的方向分。
